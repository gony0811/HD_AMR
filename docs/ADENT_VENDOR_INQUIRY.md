## 1. REST API 전반

### 1.1 v3 REST API 전체 사양서 제공 가능 여부 ✅⚠️
**질의** — Swagger JSON 또는 문서 형태의 전체 엔드포인트 목록, 인증 방식, 기본 포트.

**회신** — `/api/v3` 로 접속하면 **실 로봇과 연동되는 페이지에서 인터페이스 테스트** 가능. 별도 **인증 없음**, **80 포트** 사용.

**ACS 해석**
- 문서 산출물은 제공되지 않음 → 로봇의 `/api/v3` Swagger에서 **`swagger.json` 을 직접 수집·보관**하여 사내 계약 사본으로 삼는다.
- 실물 확보 전까지는 회신·캡처로 재구성한 **`ADENT_TARSM_V3_OPENAPI.yaml`**(ACS 초안, 신뢰도 CONFIRMED/INFERRED/UNCONFIRMED 표기)을 참조 사양으로 사용한다. swagger.json 확보 시 그것이 정본이 되고 초안은 대조용으로만 남긴다.
- 인증 없음 + 80 포트 = 네트워크에 접근 가능한 누구나 로봇을 이동시킬 수 있음 → **폐쇄망 전제 명문화 + 방화벽/세그먼트 분리**를 리스크 시트 항목으로 등록.

## 2. 좌표 이동 `POST /api/v3/robot/go`

### 2.1 응답 스키마 ✅⚠️
**회신** — 성공 `{code: 0, data: {}}` / 실패 `{code: N, message: ""}` 공통 envelope.

**ACS 해석** — `code` 값 목록(실패 코드 enum)은 미제공. 2.3·5.1과 함께 2차 질의로 이관.

### 2.2 동기/비동기 ✅
**회신** — 기본적으로 **명령 수리(비동기)**. 진행 상태는 `GET /api/v3/robot/status` 의 **`schedule` 필드**로 확인.

**ACS 해석** — 온보드 SW는 `/go` 발행 후 `status` 폴링으로 도착을 판정한다(VDA 5050 회신 §3.1 정합). 폴링 주기·`schedule` 값 목록은 미확정 → 2차 질의.

### 2.3 이동 실패 시 동작 ⚠️
**회신** — `GET /api/v3/robot/status` 의 **`error` 필드**로 확인 가능.

**ACS 해석** — 확인 경로는 확보. **에러코드 목록은 여전히 미제공**(5.1과 동일 건) → `drivingFailed` / `localizationLost` / `equipmentError` 매핑 테이블을 만들 수 없으므로 2차 질의 최우선.

### 2.4 stopFlag 의미 ✅
**회신**
- `true`: 해당 지점에 **정차하고 각도까지 보정**
- `false`: 해당 지점 **근처에서 정차하고 바로 다음 목적지로 이동**

**ACS 해석** — 검사 정차점은 코봇 정렬 전제(노드 theta = 벽 정면, 사양서 §4.4)가 있으므로 **항상 `stopFlag=true`**. `false` 는 경유점 전용이며 현 계약에 경유점 개념이 없으므로 사용하지 않는다. 각도 보정 결과가 `allowedDeviationTheta`(기본 0.1 rad) 도착 판정과 맞물린다.

### 2.5 좌표 프레임 ✅
**회신** — **SLAM 맵 원점 기준이며 원점은 맵 좌측 하단**. `rz` 는 **X축 기준 CCW 라디안** 맞음.

**ACS 해석** — 통합맵 층 타일 배치 시 원점이 좌하단이므로 **모든 타일 오프셋이 양수**가 된다. 층별 좌표 → 통합맵 좌표 오프셋 테이블을 이 전제로 정의한다.

### 2.6 이동 중 재호출 ✅ — **주의 항목**
**회신** — `/go` 는 **이동 작업을 추가 등록하는 메소드**로, **다음 목적지로 큐에 등록**된다. 중간에 이동을 멈추고 다른 목적지로 보내려면 **`POST /api/v3/robot/state` 호출이 필요**.

**ACS 해석 (설계 영향 大)**
- VDA 5050 회신 §3.3 "신규 orderId 수신 = 이전 Order 즉시 폐기"를 `/go` 재호출만으로 구현하면 **이전 목적지가 큐에 남아 로봇이 엉뚱한 지점을 먼저 경유**한다.
- 따라서 Order 교체·취소·emergencyStop 경로는 **반드시 `POST /robot/state`(정지/큐 클리어) → `/go`** 순서로 구현하고, 발행 후 `status` 로 큐 잔여를 검증한다.
- 증상이 "로봇 정상 동작 + 위치만 오류" 형태라 **조용한 오검사** 계열 → S/W 검증 항목으로 등록.

### 2.7 이동 중지 ✅
**회신** — **`POST /api/v3/robot/state`** 호출 (api/v3 문서 예제 참고).

**ACS 해석** — REST 단독으로 주행 정지가 가능하므로 **Modbus 주행 정지(Holding 12) 의존을 제거**할 수 있다. 다만 `state` 의 파라미터 사양(정지 / 큐 전체 삭제 / 재개 구분)은 미확인 → 2차 질의.

## 3. 재측위 (Modbus PoseSearch, Holding 20~26) ❌ 전건 미회신

3.1. 탐색 범위 — 지정 좌표 주변 **국소 탐색**인지 맵 전역 탐색인지, 탐색 반경.
3.2. 완료/실패 판정 — 확인 방법(레지스터? 소요 시간 상한?).
3.3. 맵 일치율(Input 30) — 정확한 의미, 정상 주행 시 통상 범위, "측위 신뢰 가능" 임계값 권고치.

> **영향** — 층 전환 게이트(사양서 §9.2, AMR 회신 §3.2 "재측위 → 맵 일치율 임계값 통과 시에만 새 mapId 보고")의 판정 근거가 통째로 비어 있다. 2차 질의 최우선 항목.

## 4. 맵 관리 (통합 맵 운용 확인)

배경: 화물창 4개 층을 각각 스캔한 맵을 **1장의 맵으로 병합해(층별 타일 배치) 단일 맵으로 운용**하고, 해당 층 이동 시 재측위(InitPose)로 층 전환.

### 4.1 맵 편집/병합 도구 ✅
**회신** — 가능. 각 층별 맵을 작성하고 **맵 에디터로 복사·붙여넣기** 하는 방식 맞음. 절차는 **① 구역별 맵 스캔·생성 → ② 모든 구역을 포함하는 통합맵 생성 → ③ 통합맵 위에서 각 거점 등록**.

**ACS 해석 (설계 영향)** — 거점(node)은 **통합맵 좌표계에서만 유효**하므로 층별 맵에서 잡은 거점은 재사용되지 않는다. 층별(u,v) → 통합맵(x,y) 오프셋 테이블이 온보드 SW의 명시적 산출물이 되며, ACS 계약(층별 mapId·층별 좌표)은 AMR 회신 §3.2대로 그대로 유지한다.

### 4.2 최대 맵 크기 ✅
**회신** — 권장 **200 m × 200 m 이하 (40,000 ㎡ 이하)**.

**ACS 해석** — 화물창 층 실치수 기준 2×2 타일 배치 + 타일 간 여유를 계산해 한도 내인지 확인 필요(별도 계산 과제).

### 4.3 단일 맵 내 물리적 분리 구역 다수일 때 측위·주행 제약 ❌
> **영향** — 층 4개의 형상이 유사하므로 **전역 재측위가 다른 층 타일로 수렴할 위험**이 있다. 3.1(국소/전역 탐색)과 묶어 2차 질의.

### 4.4 복수 맵 저장·활성 맵 전환 기능 ❌ (통합맵 불가 시 대안 확인용)
> 통합맵이 가능하다는 회신을 받았으므로 우선순위 하향. 참고용으로만 재질의.
