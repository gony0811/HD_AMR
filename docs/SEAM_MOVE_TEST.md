# 용접 위치 시험 (seamStartW → 코봇 TOOL)

ACS 가 VDA5050 `startWeldInspection` 으로 보낸 **용접선 시작점**(`seamStartW`, 맵 좌표)으로
코봇 TOOL 이 실제로 가는지 확인하는 시험 화면이다. Desktop 앱 `RECIPE › 용접 위치 시험`
(`SeamMoveTestViewModel` / `SeamMoveTestView`).

검사 운영 경로(레시피·티칭 경유점)와는 **별개**다. 운영 경로는 티칭 자세로 이동하고 `seamStartW` 는
검사 방향(수평/수직) 유도에만 쓴다(§4.4). 이 화면은 그 좌표 자체가 물리적으로 맞는지를 보는 도구다.

## 1. 좌표 사슬

```
seamStartW (맵 좌표, m)          ← ACS 발행. 도면 좌표에 T_W_D 적용 후 전송(AMR은 도면 해석 불요)
  → z 기준 보정 (− level_z)      ← §3 참조
  → 면 법선 산출                  ← §4 (wall_code = 앙각, 노드 theta = 방위각)
  → standoff 후퇴 (법선 반대)
  → p_B = (T_W_A · T_A_B)⁻¹ · p_W  /  R_B = R_WB⁻¹ · R_W
       T_W_A : AMR SLAM pose (맵 → 차체, x·y·yaw)
       T_A_B : 장착 보정 (차체 → 코봇 BASE), tz 는 텔레스코픽 스트로크만큼 가변
  → MoveL (tool=지정, user=0, 광축이 면 법선을 향하는 자세)
```

계산은 전부 `HD.AMR.App/Service/Inspection/SeamBaseTransform.cs` 한 곳에 있고
(`SeamBaseTransformTests` 가 왕복·standoff·스트로크·z 기준을 고정), 화면은 입력·읽기·이동만 한다.
맵→BASE 역변환은 `MapCalibration.MapPointToBase`(기존 `BasePointToMap` 의 역).

**AMR 은 도면과 캘리브레이션할 필요가 없다.** T_W_D(도면→맵)는 ACS 만 갖고 발행 직전에 적용하며,
그 기준점 자체가 로봇이 보고한 SLAM 위치로 캡처된다. 따라서 AMR 에 필요한 것은 자기 측위 pose 하나다.

## 2. 사용 절차

1. **용접선 입력** — `seamStartW` 를 직접 넣거나, 수신한 액션 JSON 전문을 붙여넣고
   `액션 JSON 해석해서 채우기`(`WeldInspectionActionParser` 를 그대로 사용 — 운영 경로와 같은 해석기).
2. **기준 확인** — AMR SLAM pose·텔레스코픽 스트로크·`T_A_B`·광축 툴축은 자동으로 읽는다.
   노드 theta(벽 정면 방향)는 액션에 없으므로 필요하면 order 노드의 `nodePosition.theta` 를 입력한다
   (미입력 시 AMR yaw 사용).
3. **면 선택** — `wall_code` 를 고른다(액션 JSON 을 붙여넣으면 자동으로 채워진다). §4.
4. **z 기준 보정** — §3.
5. **환산 결과 확인** — 맵/BASE 좌표, 면 법선, 이동 목표 pose, BASE 원점까지 거리, 경고 문구.
6. **이동** — 안전 확인 체크 후 `접근점으로 TOOL 이동`. 이동 로그에 현재 TCP 대비 **자세 변화량(도)** 이 남는다.

## 3. z 기준 (실기 확인 필요) `[N17]`

ACS 의 T_W_D 는 **2D(x, y, yaw) 강체변환**이라 z 는 변환되지 않고 **도면 전역 z**(선창 바닥 = 0)가
그대로 실려 온다. AMR 은 자기 바닥을 0 으로 보므로 L2 이상에서 층 바닥 높이만큼 어긋난다.

| 항목 | 값(예: L2, 층 바닥 3.2 m) |
|---|---|
| 수신 `seamStartW[2]` (도면 전역 z) | 4.5 m |
| 층 바닥 `level_z[1]` | 3.2 m |
| AMR 바닥 기준 높이 | 1.3 m |

L1 은 `level_z[0]=0` 이라 두 값이 같아 차이가 드러나지 않는다 — **지금까지 단층 E2E 만 했기 때문에
발견되지 않았다.** 화면의 `z 기준 보정` 에 해당 층 바닥 높이를 넣으면 맞는다. `level_z` 는 VDA 계약으로
전달되지 않으므로, 근본 해결은 둘 중 하나이며 §10 N17 로 협의 중이다:

1. **ACS 가 z 를 층 바닥 기준으로 바꿔 발행** (권장 — AMR 이 `level_z` 를 몰라도 된다)
2. z 를 선창 전역으로 두고 `level_z` 를 계약에 추가

※ 현재 운영 경로는 seam 의 **Δz**(끝점−시작점)만 방향 유도에 쓰므로 기준면과 무관하다. 즉 이 문제는
좌표를 **위치로 쓰기 시작하는 순간**(이 시험 화면, 그리고 향후 좌표 기반 위치 결정)부터 영향을 준다.

## 4. 면 법선과 TOOL 자세 (`wall_code`)

ACS 는 벽 법선(`wallNormalW`)을 **보내지 않는다**(§8.1 — 툴 자세는 AMR 책임). 대신 `drawingPos.wall_code`
와 정차 노드 theta 두 값이면 법선이 정해진다.

| 성분 | 출처 | 비고 |
|---|---|---|
| **방위각** | 정차 노드 theta (없으면 AMR yaw) | 맵 프레임과 탱크 자세를 잇는 유일한 값 — 아래 표 참조 |
| **앙각** | `wall_code` 의 면 자세 | 수직벽 `SM`·`PM`·`F`·`A` = 0° / 바닥 `B` = −90° / 천장 `T` = +90° / 하부 챔퍼 `SL`·`PL` = −45° / 상부 챔퍼 `SU`·`PU` = +45° (KC-2B 팔각 단면, 전 챔퍼 45° 등각) |

이 법선으로 두 가지가 정해진다.

1. **접근점** = seam − standoff × 법선. 바닥·천장·챔퍼에서도 면에서 제대로 떨어진다
   (수평으로만 물리던 초기 구현의 한계 해소 — 바닥이면 위로, 천장이면 아래로 뜬다).
2. **TOOL 자세** — **광축**(카메라 페이지의 `Camera.Align.DepthAxis`, 기본 툴 +Z)이 법선을 향하도록 회전.
   광축 둘레의 남은 1자유도는 `spin`(도)으로 준다 — 0° 는 용접선 방향(`seamEnd` 없으면 벽면 수평 탄젠트) 기준.

   **spin 부호 주의**: spin 은 **광축 둘레** 회전이라 광축이 툴 −Z 로 설정된 설비에서는 툴 RZ 와 부호가
   반대다. "툴 좌표계 RZ 를 반시계 90°" 를 원하면 — 광축 +Z: `spin = +90`, 광축 **−Z: `spin = −90`**.
   광축이 ±X·±Y 면 애초에 RZ 와 대응하지 않는다. 화면이 현재 광축에 맞는 부호를 안내한다.

`wall_code` 를 비우거나 `면 법선 자세로 이동` 을 끄면 **현재 TCP 자세를 유지**한 채 위치만 바꾼다(수평 후퇴).
미정의 코드는 경고하고 같은 폴백으로 처리한다.

> **수직벽 4종(`PM`·`SM`·`F`·`A`)은 wall_code 로 구분되지 않는다.** 넷 다 앙각 0° 라 법선 방위는 전적으로
> theta 가 정한다 — 같은 theta 로 `PM`↔`SM` 을 바꿔 봐야 **자세가 완전히 동일**하다. 운영에서는 ACS 가
> 벽마다 다른 theta(마주보는 벽은 180° 차이)를 보내므로 문제가 없지만, 시험 화면에서 theta 를 고정한 채
> wall_code 만 바꾸면 "아무 변화가 없다"로 보인다. 마주보는 벽을 시험하려면 **theta 를 180° 바꿔야** 한다.
> wall_code 가 실제로 자세를 바꾸는 경우는 **면 자세가 다를 때**뿐이다(수직벽 ↔ 바닥/천장 ↔ 챔퍼).

### 4.1 방위각(벽 정면 방향)의 출처

`정차 노드 theta 를 벽 정면 방향으로 사용` 체크가 이 표를 고른다. 어느 쪽이든 **법선의 앙각·standoff·
자세 계산 방식은 같고, 방위각의 출처만 달라진다.** 화면의 환산 결과에 실제로 쓴 출처가 표시된다.

| 상태 | 방위각 | 성격 |
|---|---|---|
| 체크 ON | 입력한 노드 theta | **고정값** — 로봇이 움직여도 목표가 변하지 않는다. 실제 order 를 재현할 때 |
| 체크 OFF + AMR 측위 있음 | AMR SLAM yaw | **실시간** — 로봇이 돌면 목표도 따라 돈다(0.5초 주기 재계산, 이동 직전에도 재계산) |
| 체크 OFF + 수동 pose | 수동 입력 yaw | 계산 전용(이동 불가) |
| 체크 OFF + 측위 없음 | **0°(맵 +X) 가정** | 숫자가 조용히 틀리는 경우 — 경고를 띄운다. 이동은 어차피 막힌다(측위 없음) |

> **AMR yaw 폴백의 전제**: "AMR 이 벽을 **정면으로** 보고 서 있다". 벽과 **나란히** 세워 두고 코봇만
> 옆으로 뻗어 검사하는 배치라면 이 전제가 깨지므로 노드 theta 를 직접 입력해야 한다.
>
> **판정은 방위각이 아니라 법선 거리로 한다.** 화면은 `면까지 거리(법선 방향)` 를 표시하고,
> 0 이하(면이 코봇과 같은 평면이거나 뒤) 또는 standoff 미만(접근점이 BASE 평면 뒤로 넘어감)이면 경고한다.
> BASE→용접선 **방위**와 법선 방위가 크게 벌어지는 것은 **정상**이다 — 벽이 0.5 m 앞이고 용접선이 벽을
> 따라 옆으로 1.3 m 있으면 두 방위는 69° 벌어지지만 배치 자체는 올바르다.

> 이 자세는 **좌표 환산 확인용**이다 — 실제 검사 자세는 레시피·티칭(경유점)이 결정하며 이 화면이 대신하지 않는다.

### 4.2 `T_A_B.rz` 현장 검증 (조그 대조)

`T_A_B.rz` 가 틀리면 **위치와 자세가 함께** 그만큼 돌아간다 — 툴이 엉뚱한 곳에서 엉뚱한 쪽을 본다.
좌표 계산을 거치지 않고 **조그 한 번으로** 검증할 수 있다. 화면의 `이 값(rz=…)대로면 조그 시 …` 줄이
저장값의 예측을 보여 주므로, 실제 조그 방향과 대조하면 된다.

| BASE +X 조그가 가는 방향 | BASE +Y 조그가 가는 방향 | 실제 `T_A_B.rz` |
|---|---|---|
| AMR 전방 | AMR 좌측 | `0°` |
| AMR 좌측 | AMR 후방 | `90°` |
| AMR 후방 | AMR 우측 | `180°` |
| AMR 우측 | AMR 전방 | `−90°` |

> AMR 차체 규약: **+X = 전방**(주행 방향 = SLAM yaw 방향), **+Y = 좌측**. 장비마다 이 라벨이 다를 수
> 있으므로 판정은 **축 이름이 아니라 물리 방향**(전/후/좌/우)으로 할 것.
>
> 조그 전 **활성 작업물 프레임을 0(BASE)으로** 되돌릴 것 — wobj 가 걸려 있으면 "BASE 조그"가 그 프레임
> 기준이 되어 판정이 뒤집힌다. 이동 후 TCP pose 의 x 가 실제로 증가했는지 숫자로도 확인하면 확실하다.

`T_A_B` 는 이 화면 말고 **QR 측위**(`QrLocalizationService`)도 쓴다 — 틀린 값은 측위 결과까지 오염시킨다.

## 5. 안전 설계

- 이동 목표는 용접선 그 점이 아니라 벽에서 `standoff`(기본 400 mm) 물러난 **접근점**이다.
  100 mm 미만이면 경고하고 이동 버튼을 막는다.
- **이동 직전에 AMR pose·스트로크를 다시 읽어 목표를 재계산**한다 — 화면 표시값이 낡아도 엉뚱한 곳으로 가지 않는다.
- AMR 이 2.5 초 이상 정지해 있어야 이동할 수 있다(주행 중 이동 금지).
- 수동 AMR pose 입력은 **계산 전용** — 그 상태로는 이동하지 않는다.
- 이동 전 역기구학을 먼저 풀어 도달 불가면 명령을 보내지 않는다(rc=112 계열 사전 차단).
- 속도는 1~30 % 로 제한한다. 자세는 `wall_code` 가 있으면 면 법선 자세로, 없으면 현재 TCP 자세 유지.
- `T_A_B` 미보정(전부 0)이면 이동을 거부한다 — 환산 자체가 의미 없기 때문.
- 면 법선 자세는 손목을 크게 돌릴 수 있어, 이동 직전 현재 TCP 와의 **자세 변화량**을 계산해 로그에 남기고
  45° 를 넘으면 한 줄 더 경고한다(IK 사전 점검과 별개).

## 6. 결과 해석

| 증상 | 의심 지점 |
|---|---|
| 수평(x,y)은 맞는데 높이만 일정하게 어긋남 | z 기준(§3) 또는 `T_A_B.tz`·텔레스코픽 스트로크 |
| 전체가 일정 방향으로 평행 이동 | `T_A_B` 의 tx·ty, 또는 AMR 측위 오차 |
| 자세를 바꾸면 오차가 달라짐 | `T_A_B` 회전 성분(rx·ry·rz) 또는 공구 TCP |
| AMR 재정차마다 오차가 달라짐 | SLAM 측위 재현성 — 정차 오차는 원래 이 경로로 흡수된다(§4.2 allowedDeviation) |
| **TOOL 이 90° 돌아 면을 옆으로 봄** | 벽 정면 방향(방위각)이 90° 틀렸다 — AMR 이 벽과 **나란히** 서 있는데 노드 theta 없이 AMR yaw 로 폴백한 경우가 전형. 노드 theta 를 입력하면 해결된다. 판별은 `면까지 거리(법선 방향)` 로 — 0 이하이거나 음수면 방향이 반대다(§4.1) |
| 용접선이 로봇 정면이 아니라 옆에 있음 | **정상일 수 있음** — 벽이 가깝고 용접선이 벽을 따라 옆으로 떨어져 있으면 그렇게 보인다. `면까지 거리` 가 standoff 보다 크면 배치는 올바르다 |
| TOOL 이 면을 비스듬히 봄 | 노드 theta(방위각) 또는 `wall_code`(앙각) — 둘 중 하나가 실제 면과 다름 |
| **`wall_code` 를 바꿔도 자세가 그대로** | 수직벽 4종은 원래 구분되지 않는다(§4) — 마주보는 벽은 theta 를 180° 바꿀 것. 또는 `면 법선 자세로 이동` 체크가 꺼져 있음 |
| **광축이 면이 아니라 면을 따라(예: 선미) 향함** | 명령 자세에서 광축은 법선, **툴 X 는 면 접선**이다. 실제 카메라 광축이 설정(`Camera.Align.DepthAxis`)과 다른 툴축이면 딱 90° 틀어져 접선 방향을 본다 — 툴 좌표계로 광축 방향 조그를 해서 영상이 가까워지는 축을 확인할 것 |
| 자세는 맞는데 화면 회전이 90° 틀림 | `spin` 값, 또는 광축 파라미터(`Camera.Align.DepthAxis`) 설정 |
| pose 의 `ry` 가 ±85~90° 이고 `rx`·`rz` 가 요동침 | **정상일 수 있음** — 툴 X 가 연직에 가까우면(예: 수직벽 + `spin ±90`) ZYX 오일러각이 짐벌락에 들어가 `rx`·`rz` 가 서로를 상쇄하며 흔들린다. 오일러 삼각형 대신 환산 결과의 **`자세 확인(맵)`** 줄(광축·툴X·툴Y 방향)로 판단할 것 |
| 정차각(theta)을 바꿨는데 자세가 그대로 | theta 입력이 반영되지 않은 것 — `정차 노드 theta` 체크가 꺼져 있으면 AMR yaw 를 쓴다. 법선 방위가 theta 와 같이 도는지 `자세 확인(맵)` 줄로 확인 |
