# AMR 라이다 / 맵 API 실기 분석

확인일: 2026-09-19. 대상: `http://10.10.100.200`.
로봇이 제공한 Swagger: TARS-AMR 3.18.0, 78개 경로 / 100개 HTTP 작업.
정의 사본: [AMR_SWAGGER_2026-09-19.json](AMR_SWAGGER_2026-09-19.json).
기존 `ADENT_TARSM_V3_OPENAPI.yaml`은 사내 재구성 초안이며 이번 실기 정의와 구별한다.
이번 확인에서는 조회 GET만 실행했다. 아래 점 수는 서로 다른 시각의 단일 응답이다.

## 실측 결과

| GET 경로 | 응답 / 용도 | 확인 결과 |
| --- | --- | --- |
| `/api/v3/robot/pose` | `data.x,y,rz,lidar[],timestamp,path,fit` | 성공, 라이다 1,202점. 맵 표시의 우선 경로 |
| `/api/v3/robot/status` | `data.pose`, `lidar`, `map`, 배터리·작업·장애 상태 등 | 성공, 라이다 1,208점. 활성 맵 이름도 확인 가능 |
| `/api/v3/robot/lidar` | `data[센서][점]`: `angle,range,quality` | 성공, 필터링 적용. 센서별 점 수 1,264 / 0 |
| `/api/v3/robot/lidar/all` | 위와 같은 극좌표 형식 | 성공, 점 수 1,351 / 0 |
| `/api/v3/map/info` | 현재 로드된 맵, 이미지·플랜 포함 | 성공, `260902_105517.map`, 307×427 |
| `/api/v3/map/size` | `name,width,height` | 성공. 물리 해상도는 포함하지 않음 |
| `/api/v3/robot/device/info` | 센서 구성 및 설치 오프셋 | 성공. 필요한 `lidars`만 추출해 사용; 전체 설정 로깅 금지 |
| `/api/v3/robot/obstacle` | Swagger상 장애물 맵 좌표 | 이번 조회는 Swagger HTML을 반환. JSON API로 사용하기 전 추가 확인 필요 |

문서상 추가 조회 경로: `/api/v3/map` (맵 목록), `/api/v3/map/cache` (실시간 맵 PNG),
`/api/v3/map/cost/` (비용 지도 PNG), `/api/v3/robot/brief` (Modbus 포함 상태),
`/api/v3/plan/*/list` (거점·가상벽·구역 등). 이 경로들은 이번 실기 응답 미검증.

## 권장 데이터: robot/pose

아래는 실제 응답에서 점 하나만 남기고 반올림한 예시다.

```json
{
  "code": 0,
  "data": {
    "x": 5.940306,
    "y": 13.612385,
    "rz": 1.570796,
    "lidar": [{ "x": 4.389621, "y": 12.251699 }],
    "timestamp": 1789747822226,
    "path": [],
    "fit": 0.7146
  }
}
```

각도 API 첫 점 `angle≈2.3561945`, `range≈2.192`와 활성 센서의 오프셋
`x=0.19, y=0, rz=0`을 로봇 포즈에 적용하면 위 점의 맵 좌표와 일치한다.
따라서 `pose.lidar`는 맵 좌표로 변환된 미터 단위 점이라는 강한 실측 근거가 있다.
추가 로봇 회전·이동 변환을 적용하면 이중 변환이 된다. 이동 중 현장 정합 검증은 아직 하지 않았다.

활성 센서는 설정상 `leuze_rsl235` 1개이며 두 번째 센서는 비활성이다.
극좌표 값은 약 +135° ~ -135° 범위이며 전체 샘플은 1,351개다.
`quality`의 정확한 의미/정상 임계값과 내부 필터링 규칙은 Swagger에 명시되지 않았다.

## 대시보드 연결 설계

1. `/map/info` 또는 `/robot/status.data.map`으로 활성 맵을 식별하고 배경과 일치시킨다.
2. `/robot/pose` 응답 하나에서 포즈와 라이다 점을 함께 갱신한다.
3. 최초 조회 주기는 500ms 정도로 시작하되 실제 지연을 측정해 조정한다. 이는 검증된 최대 주기가 아니다.
   이전 요청 완료 전에 다음 요청을 겹치지 않고, 화면 비활성화 시 폴링을 중단한다.
4. 지도는 재사용하고 최신 점만 그리는 Avalonia 커스텀 렌더링 레이어를 둔다.
   약 1,200개 컨트롤을 매번 생성하는 대신 하나의 그리기 작업에서 점들을 표시한다.
5. timestamp의 갱신 여부 및 로컬 수신 시각을 확인해 오래된 스캔을 구별한다.
   timestamp의 단위는 값의 형태상 Unix ms로 보이지만 공식 정의는 아직 미확인이다.
6. 통신 실패, 맵 변경, 잘못된 좌표, 미확정 해상도에서는 점을 숨기고 상태를 표시한다.

좌표 변환 (`r`: m/픽셀, `H`: 이미지 높이, `(ox,oy)`: 맵 원점):

```text
pixelX = (lidar.x - ox) / r
pixelY = H - (lidar.y - oy) / r
```

현재 맵 내용의 원점은 `(0,0)`. 맵 내용·info·size 응답 어디에도 `resolution`이 없다.
307×427은 PNG 크기와 같아 픽셀 크기로 판단하며, 이 값만으로 m/픽셀을 확정할 수 없다.
정확한 해상도는 벤더 설정 또는 맵 제작 규격으로 확인해야 한다. 임의 기본값을 확정값처럼 사용하지 않는다.

대시보드는 `/robot/pose`를 1초마다 폴링하고, 전용 Avalonia 렌더링 컨트롤로 라이다 점·AMR 포즈를
맵 위에 표시한다. 확대/축소 범위는 50~500%이며 `fit` 값은 "맵 신뢰도"로 표시한다.
