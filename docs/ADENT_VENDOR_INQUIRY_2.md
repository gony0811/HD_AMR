## A. 재측위(PoseSearch)와 통합맵 측위 — 최우선

층 전환을 "엘리베이터로 층 이동 → 해당 층 위치에서 재측위 → 성공 시에만 그 층으로 인정"하는 게이트로 설계하고 있어,
**재측위의 성공/실패를 프로그램이 판정할 수 있어야** 층 전환 자체가 성립합니다. 1차 3장 전건이 미회신 상태입니다.

**A-1. 탐색 범위 (1차 3.1)** — PoseSearch(Holding 20~26)는 **지정 좌표 주변 국소 탐색**입니까, 맵 전역 탐색입니까? 국소라면 탐색 반경은 얼마이며, 파라미터로 조정 가능합니까?

**A-2. 완료/실패 판정 (1차 3.2)** — 재측위 완료·실패를 외부에서 확인하는 방법(레지스터 값? REST 필드?)과 통상 소요 시간·타임아웃 상한을 알려주십시오.

**A-3. 맵 일치율 (1차 3.3)** — Input 30 "맵 일치율"이 무엇과 무엇의 일치율인지, 정상 주행 시 통상 범위, **"측위를 신뢰해도 된다"고 판단할 임계값 권고치**를 알려주십시오.

**A-4. 유사 형상 구역 오수렴 (1차 4.3)** — 통합맵에 **형상이 매우 유사한 층 타일 4개**가 들어갑니다.
- 재측위가 **다른 층 타일로 잘못 수렴**할 가능성이 있습니까?
- 있다면 이를 방지하는 방법(초기 추정 좌표 강제, 탐색 범위 제한, 구역 지정 등)이 있습니까?
- 오수렴이 발생했을 때 **외부에서 검출할 수 있는 지표**(일치율 외)가 있습니까?

> 배경: 층을 오인한 채 주행하면 로봇은 정상 동작하지만 **검사 위치만 틀리는** 형태가 되어 사후 검출이 어렵습니다. 이 경로를 차단하는 것이 이번 연동의 안전 요건 중 하나입니다.

**A-5. REST 재측위** — 재측위를 **REST(`/api/v3`)로도** 지시할 수 있습니까? (현재 Modbus 경로만 확인됨. 가능하다면 엔드포인트·파라미터를 알려주십시오.)

## B. 에러·상태 스키마 — 장애 처리 설계 전제

**B-1. 에러코드 목록 (1차 2.3 / 5.1)** — 로봇 에러 코드(Modbus Input 11 및 REST 실패 응답의 `code`) **전체 목록과 의미**를 표 형태로 요청드립니다.
관제 측에서 각 코드를 **주행 실패 / 측위 상실 / 장비 이상 / 비상정지 중** 4개 분류로 매핑해야 하며, 분류가 곧 재시도·스킵·알람 정책을 가릅니다.

**B-2. `GET /api/v3/robot/status` 응답 스키마** — 전체 필드 목록과 함께, 특히
- `schedule` 필드가 가질 수 있는 **값(상태) 목록과 각 의미** — 특히 "이동 중 / 도착 완료 / 큐 비어 있음"을 어떻게 구분합니까?
- 목적지가 **큐에 여러 개 쌓였을 때** 남은 목적지 수·현재 목표를 알 수 있습니까?
- `error` 필드의 형태(단일 코드? 배열?)와 **에러 해소 시 자동으로 비워지는지** 여부

**B-3. 실패 응답 `code` 체계** — 성공 `{code:0}` 외에 실패 `code` 값의 범위·의미가 B-1의 로봇 에러코드와 같은 체계입니까, 별개의 API 레벨 코드입니까?

**B-4. 도착 판정** — `stopFlag=true` 정차 시 **각도 보정 완료까지 끝난 시점**이 `schedule` 상 "도착"으로 반영됩니까, 위치 도달 시점에 반영됩니까?
(정차 직후 협동로봇 동작을 시작하므로 **보정 완료 시점** 판정이 필요합니다.)

**B-5. 도착 정밀도** — `stopFlag=true` 기준 통상 정차 오차(위치 m / 각도 rad)의 실측 범위를 알려주십시오. 관제 도착 판정 허용오차를 0.08 m / 0.07 rad 로 잠정 설정해 두었습니다.

## C. 목적지 큐·정지 제어 (1차 2.6 / 2.7 회신 후속)

**C-1. `POST /api/v3/robot/state` 파라미터 사양** — 요청 body 전체 사양과 함께,
- **주행 정지**와 **큐 전체 삭제**가 구분됩니까? 정지만 하면 큐에 남은 목적지가 유지됩니까?
- 정지 후 **재개(resume)** 가 가능합니까, 아니면 `/go` 재발행만 가능합니까?
- 정지 요청이 **완료되는 시점**(감속 완료)을 확인하는 방법이 있습니까?

**C-2. 큐 최대 길이** — `/go` 로 등록 가능한 목적지 큐의 최대 개수와, 초과 시 동작(거부? 오래된 항목 폐기?).

**C-3. 큐 잔여 확인** — 현재 큐에 등록된 목적지 목록을 조회하는 방법이 있습니까? (B-2와 동일 건이면 통합 회신 부탁드립니다.)

> 배경: 관제는 **한 번에 하나의 정차점만** 발행하고 완료 후 다음을 발행하는 모델입니다. 목적지 교체 시 이전 목적지가 큐에 남아 있으면 로봇이 엉뚱한 지점을 경유하게 되므로, **교체 전 큐가 비었음을 확인**하는 절차를 넣으려 합니다.

**C-4. 비상정지와의 관계** — 관제의 기능 정지(주행 정지 + 코봇 정지) 시 `POST /robot/state` 정지를 사용할 예정입니다.
- 이 정지가 **하드웨어 비상정지(안전 회로)와 별개**인 소프트 정지가 맞습니까?
- 정지 상태에서 `/go` 를 발행하면 거부됩니까, 큐에만 쌓입니까?

## D. 통합맵 운용 (1차 4장 회신 후속)

**D-1. 타일 배치 제약** — 층 타일 간 **최소 이격 거리** 권고치가 있습니까? (미지 영역으로 분리하면 되는지, 벽으로 막아야 하는지)

**D-2. 거점 등록 후 수정** — 통합맵 위에 등록한 거점을 **좌표 수치로 직접 입력/수정**할 수 있습니까? (관제가 산출한 정차 좌표를 그대로 반영하려 합니다.) REST로 거점을 조회·등록하는 API가 있습니까?

**D-3. 맵 재스캔 시 영향** — 일부 층만 재스캔해 통합맵을 갱신할 경우, **기존 거점 좌표가 유지**됩니까? 재정렬이 필요합니까?

**D-4. 맵 버전 식별** — 현재 로봇에 적재된 맵의 **식별자/버전**을 외부에서 조회할 수 있습니까?
(관제가 도면↔맵 변환 파라미터를 맵 버전에 묶어 관리하므로, 맵이 바뀐 것을 모른 채 옛 좌표를 발행하는 사고를 막는 데 필요합니다.)

**D-5. 복수 맵 전환 (1차 4.4, 참고)** — 통합맵으로 진행하므로 우선순위는 낮으나, 복수 맵을 저장해 두고 **활성 맵을 전환**하는 기능이 있다면 그 방법(태블릿 UI / REST)을 참고로 알려주십시오. 통합맵 운용에 제약이 발견될 경우의 대안으로만 검토합니다.

## E. 운영 파라미터 (1차 5장)

**E-1. 폴링 주기 (신규)** — `GET /robot/status` 의 **권장 폴링 주기**와 rate limit이 있습니까? 관제는 2초 주기 상태 보고 + 이벤트 시 즉시 보고 모델이라 200~500 ms 폴링을 검토 중입니다.

**E-2. WorkStatus (1차 5.2)** — WorkStatus(Input 64: 대기/이동/도킹/조그)가 **REST `/go` 이동 시에도 동일하게** 반영됩니까? REST `status.schedule` 과 Modbus WorkStatus 중 어느 쪽을 정본으로 보아야 합니까?

**E-3. Wi-Fi 로밍 (1차 5.3)** — 로밍 시 TCP(Modbus)/HTTP(REST) 세션 유지 특성과 두절 시 권고 재접속 방식(타임아웃·재시도 간격).

**E-4. 동시 접속** — Modbus TCP와 REST를 **동시에 사용**해도 문제가 없습니까? 동일 제어(예: 정지)를 양쪽에서 내릴 경우의 우선순위가 있습니까?

**E-5. Swagger 스펙 파일** — `/api/v3` 의 **`swagger.json`(OpenAPI 스펙 파일) 직접 URL**을 알려주시면 사내 연동 사양 사본으로 보관하겠습니다.

> 참고: 회신 주신 내용과 Swagger 화면으로 저희 쪽에서 OpenAPI 초안(`ADENT_TARSM_V3_OPENAPI.yaml`)을 재구성해 두었습니다. 실물 스펙 파일을 받으면 그것을 정본으로 대체할 예정이며, 그 전까지 위 A~E 항목이 초안의 미확정 부분입니다.
